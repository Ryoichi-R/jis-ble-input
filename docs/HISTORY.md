# 1.6.1以前の履歴

以下は2026-11-01の修正前の記録です。チェックボックス・速度・接続操作の説明は当時の仕様であり、現行操作はルートのREADME.mdを参照してください。

# JIS BLE Input 1.6.1 設定保存・高速化版

送信するSurfaceで確定した日本語の文章を、Bluetoothキーボードの操作として別のWindowsへまとめて入力する試作です。**受信側へのソフト導入・コマンド実行は不要で、通信はBluetoothのみ**です。

この版は**1.6.1 設定保存・高速化版**です。「文章をまとめて入力」1回で、送信開始時の文章全体を順番に入力します。1文字ごとの確認ボタンはありません。日本語モードは、旧版の文字コード・日時・Enterの異常への対策として、各文字の前でIMEオンとひらがなモードを指定し直します。英数字モードは以下の直接入力方式を使います。

**2026-11-01 JST、前版の一括入力版について、メモ帳とGoogle側で正常動作した利用者報告を得ました。** 具体的な試験文章・文字数・コードポイント列は未取得で、長文や全入力欄への対応は未確認です。 日本語Microsoft IMEが選択され、ローマ字入力で、F5による文字コード変換が使える環境が前提です。新旧IMEの互換設定は利用者回答でも未確認であり、設定変更済みとは扱いません。手動確認版は今回の目的を満たさないため通常操作から外しましたが、これだけであらゆるIME・入力欄への対応が確定したわけではありません。

## 起動と文章の入力

1. `jis-ble-input-1.6.1-win-arm64.zip`を**送信するSnapdragon Surfaceで**新しいフォルダーへ全体展開し、`JisBleInput.exe`を開きます。タイトルが「1.6.1 設定保存・高速化版」であることを確認します。古いアプリは終了します。受信PCには配置しません。
2. 起動すると登録済みPCからの接続待ちを自動で開始します。初回/追加の登録は「新しいPCとペアリング」を押して受信PCの標準Bluetooth設定から行い、接続先を選びます。次回は前回PCの接続・HID購読が戻ると送信先も復帰します。既存ペアリングの削除・再作成やIME設定変更は自動実行しません。
3. 「入力方法」と「入力速度」をそれぞれ選び、英数字モードなら受信Windowsの配列も選びます。受信側で入力先をクリックし、日本語モードならMicrosoft IMEのローマ字入力、英数字モードならIMEオフ（A）を確認し、どちらもCapsLockオフ・未確定文字なしにします。必要なら「受信側のIMEを準備」を1回押せます。この準備操作は選んだモードの指定だけで、文字・F5・Enterは送りません。受信側の「あ」または「A」を確認します。
4. 入力欄に**文章全体**を確定入力し、Surface側の確認チェックを入れます。改行を含むときは、受信先がメモ帳などEnterで改行できる通常の複数行欄であることも確認します。「文章をまとめて入力」を1回押します。以降は文字ごとの確認操作を必要とせず、日本語モードはIMEモード指定→文字コード→F5→確定、英数字モードは直接キー入力で進みます。受信側で別の操作やフォーカス変更をしません。
5. 完了後に文章全体を確認します。途中で文字コードや日時、再読み込み等の異常があれば「送信停止」を押します。入力済みの内容や未確定コードの自動削除・自動再送はしません。

初回の受入試験では、メモ帳の空のダミー文書に初期値の`日本語ABC橋。`を**まとめて**送り、文字コード・日時・余分な改行がないかを確認します。Chromeでも保存・投稿を行わないダミー欄に同じ文章をまとめて送ります。1文字ずつの手動確認へ戻す試験ではありません。基本一括入力の正常動作報告は得ましたが、受信側IMEの互換設定・OS/IMEのversionは未取得であり、他の環境の互換性確認や長文受入は別に必要です。

## 1.6.1: 日本語の文字と文字の間を短縮

利用者から、日本語の1文字と次の1文字の間（「日」と「本」の間など）が少し長いという報告がありました。文字と文字の間にあたる「確定後の待ち」と「次の文字の前のIMEオン・ひらがな指定の待ち」を、日本語の3段階すべてで短くしました。文字コードを変換するF5の後の待ちと、各キーを押している時間は変えていません。

| 入力速度 | 1.6.0       | 1.6.1       | 文字と文字の間（確定後〜次の文字の準備） |
| -------- | ----------- | ----------- | ---------------------------------------- |
| 標準     | 1.30秒/文字 | 1.10秒/文字 | 0.70秒 → 0.50秒                          |
| 少し速め | 1.05秒/文字 | 0.90秒/文字 | 0.55秒 → 0.40秒                          |
| 速い     | 0.80秒/文字 | 0.70秒/文字 | 0.41秒 → 0.31秒                          |

**この変更で、標準もメモ帳とGoogle側で正常動作を確認した版の待機時間ではなくなりました。** 新しい待機時間の実機受入は未実施です。文字コードのまま残る、日時に変換される、ひらがなにならないといった症状が出た場合は、短縮前の値へ戻す必要があります。英数字モードの速度は変えていません。

## 1.6.0から継続: 確認チェックの削除、入力設定の保存、より速い速度

- 送信前の「受信側の入力欄…を確認しました」チェックボックスを削除しました。接続先があれば、「文章をまとめて入力」と「続きから入力」をすぐ押せます。受信側の入力欄・IME・CapsLockは、これまでどおり送信前に目で確認してください。
- このチェックは、改行を送ってよい欄かどうかの確認も兼ねていました。削除後は、改行を含む文章では常にEnterを送ります。検索欄・投稿欄など、Enterで確定や送信が起きる欄へは、改行を含む文章を送らないでください。
- 入力方法、日本語と英数字それぞれの入力速度、受信側の配列を、送信Surfaceの`%LOCALAPPDATA%\JisBleInput\input-preferences.json`へ保存します。次回起動時は、最後に閉じたときと同じ選択で開きます。本文は保存しません。設定を読み込めない場合は、初期設定で開きます。
- 入力速度を追加しました。日本語は「速い（0.80秒/文字）」で、IMEのキー操作の順序は同じまま、待機を標準より約38%短くしています。英数字は「最速（0.05秒/文字）」です。どちらもプログラム上の設定値で、実機で文字抜けが起きないことは未確認です。乱れる場合は1段遅い速度に戻してください。

## 1.5.3から継続: 閉じて開き直すと受信PCが再接続しない不具合の修正

2026-11-01 JST、送信Surfaceと受信PCの実機で次を確認しました。

- アプリを開いたまま受信PCのBluetoothをオフ→オンすると、受信PCは自動で再接続し、送信先も戻った。
- 受信PCと接続したままアプリを×で閉じると、開き直しても受信PCは接続しに来ず、受信PCのBluetooth設定で「接続」を押しても戻らなかった。それまでは毎回、削除と再ペアリングが必要だった。
- 先にSurfaceのBluetoothをオフにして接続を切り、アプリを閉じ、Bluetoothをオンに戻してから開き直すと、受信PCは自動で再接続した。

接続中にキーボード機能（HIDサービス）が消えると、受信PCはこのキーボードの登録を外し、以後つなぎに来なくなると判断しました。WindowsのAPIには、接続を受ける側（Surface）からBLE接続を切る手段がありません。従来型Bluetooth用の切断要求も、BLE接続にはエラー1167で使えませんでした。

- ×で閉じるとき、受信PCと接続中なら、**SurfaceのBluetoothを数秒オフにして接続を切り、キーボード機能を外してからオンに戻して終了**します。上の手動手順と同じ順序です。
- この数秒間は、Surfaceにつないだマウス・キーボード・イヤホンなども切れ、その後Windowsが自動で再接続します。
- 受信PCと接続していないときは、Bluetoothを切り替えずに終了します。Bluetoothの切り替えが許可されていない場合も同様で、従来どおり再ペアリングが必要になることがあります。
- 1.5.2以前で一度閉じて受信PCの登録が外れた状態は、この版でも自動では直りません。最初の1回だけ削除と再ペアリングをしてください。

## 1.5.2から継続: 起動時の広告が中断扱いになる不具合の修正

2026-11-01 JST、送信Surface（Windows 11 ARM64）の実機で、1.5.1は起動時・手動開始のどちらも「Windowsが広告を中断しました（Aborted）」となり、接続待ちに入れないことを確認しました。単体の検証プログラムでは、正常な広告開始でもWindowsが**先に`Aborted`、続いて`Started`**を通知しました。1.5.1は最初の`Aborted`で失敗と判断して広告を止めていました。

- 開始時の`Aborted`では待機を続け、`Started`（または省略ありの開始）になれば成功とします。待機時間内に開始しないまま`Aborted`で終わった場合だけ、中断として表示します。
- 開始に失敗した後の「Bluetoothを再試行」は、HIDサービスを作り直してから開始します。1.5.1では失敗状態のサービスを再利用し、`Operation is not valid due to the current state of the object`で再試行できませんでした。
- アプリを閉じると「起動できませんでした / InvalidOperationException」と表示される不具合（1.3.0にもあり）を修正しました。終了処理の中で直接ウィンドウを閉じず、終了イベントの後に閉じます。

同じ検証プログラムで、新規発見不可（`IsDiscoverable=false`）の広告は8秒後も`Created`のままで、開始しませんでした。この環境で「新規発見を終了」を押すと、登録済みPCも再接続できなくなる可能性があります。この版ではこのボタンを変更していないため、使わないでください。

## 1.5.1: 起動タイムアウトと再試行不能の修正

利用者提供の画面で、1.5.0の開始が`TimeoutException`になり、接続操作のボタンがすべて無効になったことを確認しました。画像には失敗段階や広告状態がないため、実機側の直接原因は断定できません。コードでは、広告開始を`Started`だけで判定し、省略ありの開始状態や中断状態を適切に扱わず待ち続ける不備と、失敗後に再試行できない不備を確認しました。

- 起動時は、以前に動作した接続可能・新規発見可能の広告設定へ戻します。前回PCの照合・ユーザーが確認してからの本文送信は維持します。新規発見可能はペアリングの自動承認を意味しません。
- `StartedWithoutAllAdvertisementData`は広告要求の開始として扱い、データの省略があることを表示します。PC接続・HID購読が成立したという意味にはしません。`Aborted`は待機を続けず、その状態と取得できたBluetoothErrorを表示します。
- イベント通知に加え現在の広告状態を100msごとに確認し、通知欠落があっても開始を検知します。広告の停止→開始を順番に確認し、古い停止/開始通知が次の処理へ混ざることを抑えます。
- 失敗後も**「Bluetoothを再試行」**を押せます。作成済みのHIDサービスは再利用し、作成途中で失敗した場合は登録イベント・参照を片付けてから再作成します。
- **「接続診断」**に失敗段階、広告状態、取得できたエラーコードを表示します。アダプター取得/GATT作成/広告開始/広告停止を分け、取得していないエラーを成功コードで埋めません。本文・機器ID・認証情報は診断へ含めません。

まず旧アプリを終了し、1.5.1を新しいフォルダーへ全体展開して起動します。既存のペアリングで接続を待ち、開始に失敗した場合は「Bluetoothを再試行」を押せます。まだ失敗する場合は「接続診断」に出る段階・状態・コードで次の切り分けができます。ペアリングの削除・Windows再起動・Bluetooth設定のリセットは今回の修正の前提にしません。

Core 584チェック（既存553＋追加31）、Windows ARM64 build/publish、形式検査を実施しました。省略あり/中断/通知欠落/時間切れ/取消/再試行をfake publisherで検査しています。**修正版のWindows実機再接続は未確認**で、ソフトウェアの状態処理の修正を実機成功へ読み替えません。

仕様根拠: [Microsoftの広告状態一覧](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattserviceprovideradvertisementstatus?view=winrt-26100)、[広告イベントのError](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattserviceprovideradvertisementstatuschangedeventargs.error?view=winrt-26100)、[GATT広告の設定](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/gatt-server#publish-the-service)。

## 1.5.0から継続: 接続待ちと前回PCの復帰

旧版は終了時にBluetooth公開を停止し、次回も「Bluetooth公開を開始」を押すまで再開しませんでした。1.5.0は、**起動時にBluetoothの接続待ちを自動再開**します。登録済み受信PCが再接続し、HID入力の購読が戻ったことを確認できれば、前回ユーザーが選んだPCを送信先へ復帰します。別のPCしか接続していない場合に、そのPCを代わりに選ぶことはありません。

1. 初回または新しいPCを追加するときは「新しいPCとペアリング」を押し、受信WindowsのBluetooth設定から追加・承認します。登録済みPCが既にある場合は、まず既存ペアリングのまま接続待ちを使います。
2. 接続先の選択欄で送りたいPCを1回選びます。1.4以前では宛先を保存していないため、1.5の初回は選び直して記録します。
3. アプリを終了して開き直します。「起動時にBluetoothの接続待ちを再開する」がオンなら、自動で接続待ちに入り、同じPCの接続・購読が戻れば送信先を復帰します。受信側の電源・Bluetoothがオンである必要があります。
4. 送信先が戻っても、受信側の入力欄・IME・CapsLockを確認してチェックを入れ、送信ボタンで文章入力を開始します。再起動前の本文・IME操作・途中の送信を自動再開しません。

1.5.1では自動再開・初回/追加のどちらも接続可能・新規発見可能とします。1.5.0で導入した起動時の新規発見不可は撤回しました。「新規発見を終了」は登録済みPCからの接続待ちへ戻します。これらの広告設定は[Microsoft GATT Serverの仕様](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/gatt-server#publish-the-service)に従います。Windowsのペアリング情報はOSが管理し、アプリが削除・再作成することはありません。

自動再開のオン/オフと前回PCを照合する機器IDのSHA-256を、送信Surfaceの`%LOCALAPPDATA%\JisBleInput\connection-preferences.json`へ保存します。名前・生の機器ID・文章・キー列・認証情報は保存しません。方法/速度の設定は1.5系ではセッション内だけでしたが、1.6.0から保存します。接続設定を読み込めない場合は自動再開をオフにして案内し、手動操作へ進めます。保存できなかった場合は次回の手動選択を案内します。

**この機能はWindowsへ接続可能な広告を再開し、実際に戻った接続を取り込むものです。受信側へ接続を強制するAPIではありません。** 受信Windowsの再接続・購読復帰とHID定義のキャッシュによって成立が左右されます。相手が戻らない場合に接続済みと表示しません。アプリを閉じている間はキーボード機能を停止します。

Core 553チェック（既存529＋追加24）、Windows ARM64 publish、形式検査を実施しています。接続設定ファイルの保存/再読込、無効な設定の拒否、同じPCだけの照合、本文の非送信は検査しました。**アプリ終了→再起動による実機の自動再接続・HID購読復帰は未検証**です。正常動作報告がある1.3.0と従来の配布ZIPを保持しています。

## 1.4.0から継続: 入力方法と入力速度を別々に選ぶ

利用者の指定に合わせ、画面上部を**「入力方法」「入力速度」「受信側の配列」**の3つの選択欄に分けました。入力方法を変えると、その方法に対応する速度を表示します。

| 入力方法       | 入力速度 | 1文字の固定待機 |
| -------------- | -------- | --------------- |
| 日本語・混在文 | 標準     | 1.30秒          |
| 日本語・混在文 | 少し速め | 1.05秒          |
| 英数字・URL    | ゆっくり | 0.12秒          |
| 英数字・URL    | 高速     | 0.08秒          |

初期値は日本語・混在文の標準です。英数字へ初めて切り替えたときは、正常動作報告のある高速が選ばれます。日本語と英数字の速度はアプリを開いている間それぞれ保持し、入力方法を往復しても元の選択に戻ります。入力方法・速度・配列は1.5系では終了後に保存しませんでしたが、1.6.0から保存します。接続復帰用の設定は上の接続待ちの節に従います。

選択欄の下に「現在の設定」を表示します。送信前に方法・速度・配列を選び、受信側を確認してチェックを入れ、「文章をまとめて入力」を押してください。設定を変えると確認チェックは外れます。送信中・一時停止中は設定を固定し、続行も元の速度・原文・宛先世代のまま進みます。送信途中で速度を変える操作は追加していません。

日本語の標準/少し速めと英数字の高速は、正常動作報告がある1.3.0と同じキー列・待機値です。英数字のゆっくりは、同じキー列の押下・解放を各40→60msに延ばした設定です。より短い待機時間は追加していません。

英数字では初回・続行の準備に0.30秒、改行は両方式で0.35秒の待機が別途加わります。Bluetooth/APIの待ちも別途加わるため、上表は実機の文字/秒の測定値ではありません。**新しい選択UIと英数字ゆっくりの実機受入は未実施**です。Core 529チェック（既存497＋追加32）、ARM64 build/publish、形式検査を行っています。

英数字モードでは「受信側の配列」をWindows側と同じ **日本語JIS（106/109）／英語US（101/104）** から選びます。Surface側のキー配列ではなく、受信WindowsがそのBluetoothキーボードに適用する配列です。`@ : _ + = ? & % # /`などのURL記号も各配列のキー位置で入力します。受信側は未確定文字なし・IMEオフ（A）・CapsLockオフを確認してください。

英数字モードは送信開始時と一時停止からの続行時に、専用ImeOffキー（LANG2、`0x91`）を送ります。文字ごとのF5・確定Enterは使わず、URL末尾にもEnterを足しません。日本語や全角・半角カナ・ASCII以外の記号が1つでも混ざれば、IME準備キーも含めて全文を送信前に拒否します。その文章は日本語モードで送ってください。CRLF/LF/CRの改行は前版と同じく、Enterで改行する通常の複数行欄を確認した場合だけ使います。アプリ別設定や文章内の自動モード切り替えは追加していません。

英数字用の`samples/ascii-url.txt`（末尾改行なし）と`samples/ascii-printable.txt`（印字可能ASCII 95文字、末尾改行なし）を同梱します。まず受信メモ帳の空の文書で全文を入力し、大小文字・URL記号・余分な改行がないことを確認できます。URL欄で試す場合も、アプリはEnterで開く操作を追加しません。原文に末尾改行が含まれたまま検索欄へ送らないでください。

**2026-11-01 JST、1.3.0の日本語少し速め・英数字/URL高速の両モードが正常動作した利用者報告を得ました。** 試験アプリ・文章・配列・実速度は未取得で、全記号・両配列・長文・改行・再接続の受入完了とは扱いません。1.3.0の配布ZIPは上書きせず保持します。HID定義はImeOffまで拡張していますが、受信側に残る旧定義のキャッシュを自動修復・再ペアリングする機能はありません。IME状態・配列は受信側で確認します。

仕様根拠: [MicrosoftのImeOn/ImeOff定義](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/keyboard-japan-ime)、[Microsoftの106配列の文字対応表](https://github.com/microsoft/Windows-driver-samples/blob/main/input/layout/fe_kbds/jpn/106/kbd106.c)、[USB HID Usage Tables](https://www.usb.org/sites/default/files/hut1_21_0.pdf)、[QMKのJISキー位置定義](https://github.com/qmk/qmk_firmware/blob/master/quantum/keymap_extras/keymap_japanese.h)。数値のキー対応と仕様確認に使い、上流プログラムを実行・同梱するものではありません。

## 1.2.0から継続: 日本語と改行の一括入力

今回の対象は、利用者が指定した**メモ帳と通常の複数行入力欄**です。Enterで投稿・検索・保存する欄へ改行を送る機能ではありません。受信先の欄は自動判別できないため、送信前の確認チェックでEnterが改行になる欄であることを確認します。アプリ別の設定や1文字ごとの確認は追加しません。

- 本文は従来のIME変換・確定処理を使い、改行だけは未確定文字がない状態で通常のEnterを1回押し、解放して待ちます。改行にF5や文字コード`000A`/`000D`は送りません。Shift+Enterへの置き換えもしません。
- CRLFを1つの改行として扱い、LF単独・CR単独にも対応します。先頭・末尾の改行と連続する空行を削除せず、原文にない末尾のEnterも足しません。改行も1つの送信単位なので、一時停止・続行でCRLFを分割・重複しません。
- 送信開始時の原文はそのまま固定します。ただしキー操作による改行の内部表現は受信欄に従います。送信元のLF/CRLF/CRというコード列自体をすべての欄で同一に保つ保証はなく、行・空行の再現と改行コードの厳密一致は別に評価します。
- 試験用の`samples/multiline-crlf.txt`と`samples/multiline-lf.txt`を同梱します。同じ4行構成（途中に空行1つ）の日本語・英数字で、末尾にも改行があります。Surfaceで全文をコピーし、編集欄へ貼り付け、受信メモ帳の空の文書を選んで確認チェック後に「文章をまとめて入力」を1回押します。全行・空行・最後の改行が入り、コード・日時・余分な行がないことを文章単位で確認します。WPFの貼り付けで改行形式が変わる場合は、実際の編集欄の値が送信原文になります。
- Core 214チェックとWindows ARM64ビルドに成功しています。**この版の改行入力のWindows実機受入は未実施**です。正常動作報告のある前版のZIPも保持します。

Enterの意味が欄の設定に依存することは[MicrosoftのEdit control仕様](https://learn.microsoft.com/en-us/windows/win32/controls/about-edit-controls#text-and-input-styles)に従います。

## 1.1.0から継続: 長文送信の一時停止・続行と状態表示

- 「一時停止」は今の1文字のIME変換・確定とキー解放が終わった後に止まります。「一時停止準備」中にすぐ中止したい場合は「送信停止」を使います。送信停止は途中のコードや未確定文字を残すことがあり、自動削除はしません。
- 一時停止後は受信側の入力欄とIMEを確認し、確認チェックを入れて「続きから入力」を押します。文章全体を送信し直す操作ではなく、元の文章の未送信の次の文字から続きます。文字ごとの手動確認はありません。
- 一時停止中の編集は次回の下書きです。送信を続ける文章は送信開始時に固定したままで、既存の部分を再送しません。送信停止・終了後は続行できません。
- 接続先や接続世代が変わった場合は続行しません。再接続しても文章や残りを自動送信せず、受信側に残った途中入力を確認したうえで新たに送信してください。
- 文字数、進捗バー、処理時間、残り時間の目安を表示します。処理時間と見積もりから一時停止中の時間を除きます。残り時間は送信済み文字からの推定で、受信側の入力完了時刻を保証しません。
- 公開中は接続先情報を約3秒ごとに更新し、送信先の使用可否を約0.5秒ごとに確認します。更新要求が重なっても1回だけ処理します。受信WindowsのBluetooth接続を強制したり、別の機器を自動選択したりする機能ではありません。

日本語（標準）の文字に使うIMEキー列・待機時間は、メモ帳とGoogle側で正常動作した前版と同じです。改行を含む全文の検査・送信単位は1.2.0で拡張しました。**一時停止・続行・新しい接続状態表示についてのWindows実機受入は未実施**です。

長文試験用の`samples/AC-08-100.txt`（100文字）と`samples/AC-08-1000.txt`（1,000文字）を同梱します。送信するSurfaceで開き、本文を編集欄へ貼り付けて使います。ファイル末尾に改行はありません。受信側へ配置・実行するファイルではありません。まず保持できると確認した空のメモ帳で100文字から試します。旧版へ戻す場合は新版を終了し、保存してある前版のフォルダーから起動します。

## 日本語モードのIME制御

- 各文字の直前にImeOn専用キー（LANG1、HID usage `0x90`）を送り、さらに`Ctrl+CapsLock`でひらがなモードを指定します。半角/全角やCapsLock単独のようなトグルは使いません。LANG1を無視する経路に対しても、標準キー範囲の`Ctrl+CapsLock`でモード指定を試みます。
- 4桁の大文字16進コードを入力し、Shiftを解放してからF5、変換待ち、Enter、確定待ちの順に送ります。次の文字でも同じモード指定から始め、前の文字の確定後に英数モードへ戻ったまま進みません。
- 送信workerは1本で、選択した1台・接続世代・送信開始時の文章を固定します。編集後の下書きや再接続先へ残りを勝手に送ることはありません。
- 日本語（標準）は固定待機だけで1文字1.3秒、少し速めは1.05秒の設定です。100文字では標準約130秒、少し速め約105秒にBluetooth/APIの待ちが加わります。これは設定値からの計算で、実機速度の測定ではありません。
- 送信側から受信側のIME種類・バージョン・未確定文字・変換成功は読み取れません。キー列送信の成功と文章の完全一致は別です。新しいMicrosoft IMEで同方式が使えない場合、待機時間を増やすだけで対応済みとはしません。

## 現在の対応範囲

- Surface側のJIS配列・IME・タッチ入力・貼り付けで確定した文章を対象にします。読みから漢字を再変換しません。
- 日本語モードは最大2,000文字のBMP本文とCRLF/LF/CRの改行。英数字モードは同じ上限で印字可能ASCII（U+0020〜U+007E）と明示確認した改行だけに対応します。CRLFは1文字として上限・進捗を数えます。Tab・補助平面文字・結合文字・書式制御文字等を含む場合は、モード指定キーを含め1つも送らず全文拒否します。
- 本文・キー列の保存、外部ネットワーク通信、クリップボード共有はありません。Windowsの標準ペアリング情報はOSが保持します。接続待ちの自動再開設定と機器IDのハッシュだけを送信側のアプリ設定へ保存します。
- 停止・切断では未送信の残りを中止します。受信済み文字やIME未確定文字は自動修復せず、キー解放も受信側で成立した保証はありません。

## 接続と未検証事項

「新規発見を終了」は発見可能性を下げて接続可能な広告へ切り替えます。新規ペアリングの承認はWindows標準機能に従います。選択した接続先以外へ通知しません。

以前の試作にはメモ帳とChromeで短文が一致した報告がありましたが、後の失敗報告を優先します。この版にはメモ帳とGoogle側の基本一括入力の正常動作報告があります。IME制御・変換の内部状態の独立した観測、長文、再接続、HID定義のキャッシュは未検証です。旧ペアリングの古いキー定義への対策としても標準キー範囲の`Ctrl+CapsLock`を送りますが、再ペアリング不要を実測済みとはしません。
